# 智澈 ZyClear ｜ 跨品牌工业相机客户端软件

**一句话定位**：一个人从零写完的工业相机上位机——让工厂"换相机牌子、加相机型号"这两件最烦的事，都不再需要改一行业务代码。

**技术栈**：C++17 / Qt 6（Widgets·Concurrent）/ OpenCV 4.5 / 海康 MVS SDK（MvCameraControl）/ CMake / MSVC / Windows
**项目规模**：约 4800 行 C++（27 个 .cpp + 31 个 .h），八大模块分层；GitHub 开源
**我的角色**：独立开发——架构设计、相机抽象层、统一参数模型、参数面板、图像链路、构建与界面工程化，全部由本人完成

1. **懂硬件边界，也懂软件结构**：既在 SDK 层调过海康相机的枚举、回调取流与六类参数读写，也能把硬件差异抽象成稳定的上层契约——这是工业软件岗最缺的复合视角。

3. **独立全栈的落地能力**：从架构到编码、从多线程采图到深色主题界面，无协作依赖的情况下完成多轮 0→1 迭代。
4. **工程规范意识强**：统一错误码、资源 RAII、缓冲区预分配复用、编码与构建可重现，按工控软件长期稳定运行的标准要求自己。
5. **吃透陌生文档的能力**：能把一份没接触过的相机 SDK 文档读成可用的接口契约与错误处理链路。

## 项目经历

### 智澈 ZyClear ｜ 跨品牌工业相机客户端软件

**个人独立开发 ｜ 2024.xx – 至今 ｜ C++17 / Qt 6 / OpenCV / 海康 MVS SDK**

**项目描述**

面向工业视觉产线，对标海康官方 MVS 从零构建的相机客户端上位机。向下封装海康 `MV_CC_*` SDK，向上为控制、参数、视觉三大面板提供统一入口，打通"枚举 → 连接 → 参数读写与配置导入导出 → 实时拉流预览 → 多相机切换"的设备全生命周期；并内置虚拟相机，使全部功能脱离硬件即可开发与演示。设计的核心不是把界面做出来，而是解决同类软件的两个结构性问题：换厂商要改遍上层代码，加型号要手写一套参数适配。

**核心技术与实现**

- **接口 + 工厂 + 门面，把品牌差异关进一个盒子**：定义纯虚接口 `CameraInterface` 收敛相机全部行为为统一错误码契约，`CameraFactory` 单例以 `std::function` + 模板注册保存创建器，`CameraContext` 门面以"序列号 → 相机对象"映射对外提供唯一入口。界面层只凭序列号寻址，完全不感知厂商类型——新增品牌只需"继承接口 + 一行注册"，既有代码零修改。

- **类 GenICam 的统一参数模型，屏蔽六套取参接口**：各家 SDK 取参按类型拆成 Int/Float/Enum/Bool/String/Command 六套，参数集还随型号变化。设计"元信息 + 六种参数值类型（原型 `clone()` 支持拷贝）+ `QVariant` 数值 + 访问权限位域"的两层模型，六种类型全部注册 Qt 元类型；访问权限由 SDK 的 `AM_RO/RW/WO` 统一映射，参数面板据此自动决定单元格能否编辑。厂商与型号差异被限制在实现层，上层完全不感知。

- **JSON 驱动参数界面，新增型号零 C++ 代码**：硬编码参数面板必然膨胀成型号分支。改用 JSON 描述分组与参数元信息，`ParseUiJson` 单例解析，支持文件、字符串、字节流三种输入源，逐字段校验并能精确定位"哪个分组第几个参数缺哪个字段"。虚拟相机 5 组 37 个参数即由一份 JSON 完整驱动，改配置即生效、无需重编译。

- **MVD 参数面板与类型化控件族**：`CameraParamModel` 自建树形模型承载两级分组、以缓存把参数插入降为 O(1)，`CameraParamDelegate` 按类型分派到 6 种自定义编辑控件（策略模式），控件初始化流程由基类固定、子类只补编辑区（模板方法）。控件回填先断开连接再赋值以避免循环回写；拉流期间整面板自动禁用，禁止采集途中改参。

- **生产者-消费者图像队列，出图快过界面也不丢帧**：若在 SDK 回调里直接刷 UI 会阻塞回调。自实现 `CameraImageQueue`，用互斥量 + 条件变量做空闲/工作双队列，构造时预分配帧内存并循环复用，稳态零堆分配；队列满时丢最旧、保最新，取出带超时保护，取完归还空闲队列形成内存闭环。采集置于独立线程，经跨线程信号把图像投回 UI 线程，主界面永不阻塞；像素格式统一转换后，上层只面对灰度与彩色两种数据。

- **QGraphicsView 视觉窗口与像素级取色**：对比 QLabel（不能缩放拖动）与 QWidget 手绘（需自造坐标变换）后，选用场景-视图体系，借其内置坐标变换与按可见区渲染降低刷新开销。滚轮步进缩放、拖动平移、双击自适应居中；自绘图元开启 hover，把光标坐标换算为像素坐标后实时取色，显示图像尺寸与 RGB——为后续 ROI、测量、标定预先打通坐标链路。

- **事件总线解耦三大面板 + 统一错误码与工程化**：三大面板存在"连接后建树、开流后禁用、切换后同清"的交叉联动，互相持有引用会形成网状依赖。实现观察者事件总线，以位掩码定义相机事件、只通知真正关心的模块；配套统一错误码与检查宏，把"调用失败 → 可读文案 → 状态栏提示并中断流程"收敛为一行，并在连接前判定设备是否被其它客户端独占。工程侧构建由 qmake 迁移至 CMake（C++17、自动元对象与资源、UTF-8 编码、按配置选择 OpenCV 库、产物统一输出），图标样式与参数 JSON 全部编入单一可执行文件，便于分发；界面经调色板 + 300 余行 QSS 统一为深色主题。

**项目成果**

- 独立完成约 4800 行 C++，打通"枚举 → 连接 → 参数读写与配置持久化 → 实时预览 → 多相机切换"完整闭环，已在 Windows + VS2022 + Qt 6 环境编译运行，工程开源。
- 把项目两个主要变化点收敛到单点修改：新增品牌 = 继承接口 + 一行注册；新增型号 = 补一份 JSON。界面层不出现任何厂商或型号判断。
- 沉淀出一套可复用的上位机骨架（抽象接口 + 创建工厂 + 门面 + 统一参数模型 + MVD 参数面板 + 生产者消费者队列 + 事件总线），可平移至 PLC、运动控制卡、光谱仪等其它工业设备客户端。

**技术复用性**

抽象接口层、工厂注册、统一参数模型与图像队列均为设备无关的通用组件——把"相机"替换成任意工业设备，同一套分层与解耦思路即可直接复用；JSON 驱动界面的方案适用于任何批量参数配置的工控场景。

## 附：面试追问准备（不含在简历正文，投递前自行消化）

| 可能被问 | 回答要点 |
|---|---|
| 为什么非要接口 + 工厂，不写一个类搞定？ | 变化点在哪、把变化点关进一个盒子。接口层统一后，换厂商 UI 一行不改；工厂是编译期注册，插件是运行期加载 DLL，是两条演进路线，本项目选前者是因为依赖集中、部署简单。 |
| 工厂和 Qt 插件什么区别？ | 编译期绑定 vs 运行期加载；单 exe vs 独立 DLL 按需部署；第三方能否独立开发；版本能否单独升级。插件化是此项目明确的下一步。 |
| 参数模型为什么要分层，直接存 QVariant 不行？ | 直接存会丢范围、枚举候选、最大长度等元信息，UI 无法生成正确编辑器；对外只暴露一个外观类，类型差异关在实现层。 |
| 图像队列为什么用两个队列？ | 单队列每次入队都分配内存、满队列只能丢新帧；双队列预分配复用（稳态零分配）、满队列丢旧保最新（预览要最新帧）、取出归还成闭环。 |
| 为什么选 QGraphicsView？ | QLabel 不能缩放拖动；QWidget 手绘要自造坐标变换；QGraphicsView 自带场景-视图变换、只渲染可见区，后续接 ROI/测量直接在场景加图元。 |
| 项目的难点在哪？ | 答"参数模型 + 图像链路"：一个解决不同相机参数长得不一样，一个解决出图比界面快。不要答界面好不好看。 |
