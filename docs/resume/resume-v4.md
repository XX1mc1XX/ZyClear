## 一、优势与特长

1. **独立交付能力**：从需求拆解、架构设计、编码实现到联调测试全程独立完成；习惯先划清"哪些会变、哪些不变"再动手，用抽象边界换后期的返工成本。
2. **架构意识**：擅长用抽象接口与设计模式隔离变化点。本项目把"换相机品牌"和"加相机型号"两个变化点分别收敛到"一行注册"和"一份 JSON"，而不是靠不断加判断分支堆功能。
3. **主动重构的习惯**：发现重复代码或散落各处的错误处理会主动收敛——例如把各处的失败判断统一成宏、把六种编辑控件重复的取值/回写流程上提到基类；动手前先想清楚"改完之后哪个变化点被关起来了"。
4. **工程质量意识**：写并发代码时会主动考虑资源生命周期与异常兜底——图像缓冲区一次性预分配并循环复用、失败路径都有明确错误码与可读提示、句柄与线程的创建销毁成对处理。
5. **学习与迁移能力**：能较快吃透第三方 SDK 与协议文档，把陌生的硬件 C 接口抽象成稳定的上层契约；也习惯把项目沉淀的通用组件（接口层、工厂、参数模型、图像队列）平移到其他设备类型。

## 三、项目经历 · 标准版（两页简历用）

### 智澈 ZyClear —— 设备无关架构的工业相机客户端软件

**个人独立开发 ｜ 2026.0X – 至今 ｜ C++17 / Qt 6 / OpenCV 4.5 / 海康 MVS SDK / CMake**
**项目规模**：约 4800 行 C++（27 个 .cpp + 31 个 .h），按职责划分八大模块 ｜ GitHub 开源

**● 项目描述**

面向工业机器视觉现场，独立开发的一款对标海康官方 MVS 的工业相机客户端上位机，以海康工业相机 SDK 二次开发为基础，覆盖"相机枚举 → 连接控制 → 参数配置与持久化 → 实时拉流预览 → 多相机切换"的完整设备管理链路。

项目的设计目标不是"做出一个能用的界面"，而是解决这类软件长期存在的三个结构性问题：**① 换一家相机厂商就要改动上层业务代码；② 每新增一个相机型号就要手写一套参数面板适配代码；③ 相机出图节奏与界面刷新节奏不匹配，导致丢帧与卡顿。** 为此在架构上抽象出设备接口层、统一参数模型与数据驱动的界面框架，使新品牌接入与新型号适配都退化为"纯新增"操作。

**● 核心技术难点与实现**

- **设备无关的分层架构与工厂化品牌接入**：按"表现层 / 门面层 / 抽象接口层 / 设备实现层 / 支撑层"五层组织代码。定义纯虚接口 `CameraInterface`，把枚举、连接、取流、参数读写、配置导入导出等 17 个行为接口收敛为一套统一错误码契约；`CameraFactory` 单例以 `std::function` + lambda 的模板注册方式维护"厂商 → 创建器"注册表，把构造逻辑与工厂本体解耦；`CameraContext` 门面单例以"序列号 → 相机对象"映射对外提供唯一入口。接入新品牌只需"实现接口 + 一行注册"，不在任何既有文件中新增判断分支。

- **适配器封装海康 SDK 全生命周期**：将海康 `MvCameraControl` 的 C 接口封装为符合项目契约的实现类，串联 `MV_CC_EnumDevices`（GigE + USB3 双协议枚举）→ 句柄创建 → 设备占用判定（`MV_CC_IsDeviceAccessible`）→ 打开设备 → 注册图像回调 → 设置取流策略与缓存节点数 → 启动采集的完整流程；参数读写按类型分发到 Int / Float / Enum / Bool / String / Command 六套 SDK 接口，经 `MV_XML_GetNodeAccessMode` 解析节点读写权限，实现只读参数自动置灰、命令型参数渲染为触发按钮；借 `MV_CC_FeatureSave/Load` 完成 `.mfs` 配置文件导入导出。虚拟相机 `VirtualCamera` 作为接口的另一种实现，与真机共用同一套上层逻辑，脱离硬件即可跑通全链路。

- **统一参数模型屏蔽 SDK 差异**：抽象组合式模型 `CameraParam`，把各厂商命名各异的参数统一为"元信息（分组 / 名称 / 类型 / 提示）+ 取值 + 访问权限位（valid / readable / writeable）"的自描述结构；六种类型的值统一以 `QVariant` 承载并注册为 Qt 元类型，可直接在信号槽与视图索引中传递。参数层、界面层、SDK 层三方据此解耦，上层不再感知任何厂商字段命名，类型与权限差异全部被限制在设备实现层。

- **JSON 数据驱动的参数界面生成**：参数集随相机型号（面阵 / 线扫 / 3D）不断变化，硬编码维护成本高。设计 `ParseUiJson` 单例解析器，用 JSON 描述参数分组与元信息，运行时反序列化后直接构建参数模型；支持文件（含 Qt 资源）、字符串与字节流三种输入源，内置字段级合法性校验与解析进度 / 完成信号。实际面板的 5 个分组、37 个参数全部由一份 JSON 驱动，虚拟相机复用同一份配置——新增相机型号只写配置、不重编译。

- **MVD 参数面板与类型化控件族**：基于 Qt Model-View-Delegate 构建参数面板，`CameraParamModel` 按 group 分组建树（用映射表缓存组节点）、`CameraParamDelegate` 负责编辑器创建与自绘；为六种参数类型派生 `OneCustomWidget` 控件族（SpinBox / DoubleSpinBox / CheckBox / ComboBox / LineEdit / Button），以策略模式分发编辑行为——新增一种参数类型只需增加一个控件，无需改动模型与视图。编辑控件回填时先断开信号再赋值以避免程序化赋值触发回写，并按访问权限位控制单元格可否编辑；拉流期间面板整体禁用，防止采集途中改参导致帧尺寸与格式突变。

- **生产者-消费者图像队列与三线程采集链路**：自实现线程安全队列 `CameraImageQueue`，采用空闲队列 + 工作队列双结构，配合 `std::mutex` 与 `std::condition_variable` 完成阻塞取图；缓冲区在初始化阶段一次性预分配 10 帧并循环复用，采集过程不产生新的堆分配；队列满时以覆盖最旧帧的方式保证预览始终跟随最新画面，等待设 5 秒超时保护。SDK 回调线程（生产者）→ 独立采集线程 `AcquireImageProcess`（消费者，并完成 Mono / Color → Mono8 / RGB8 的像素格式统一）→ GUI 线程（只做渲染）三层之间通过线程安全队列与跨线程信号槽解耦，任何一环抖动都不会阻塞界面。

- **观察者事件总线与工程化建设**：三大界面模块之间存在"连接成功自动加载参数、开始取流禁用配置项、切换相机清空面板"等交叉联动，互相持有引用会形成网状耦合。自实现 `ListenerManager`，以位掩码标识 6 类相机事件并支持一次性批量订阅，模块之间不持有彼此引用，新增界面模块只需继承 `Listener` 接入；配套统一错误码与 `CHECK_RETURN` 宏，把"调用失败 → 转可读文案 → 送状态栏并中断当前流程"收敛为一行。工程侧用 CMake 管理构建（AUTOMOC / AUTORCC、Debug 与 Release 分配置链接、MSVC 强制 UTF-8 解决中文乱码、依赖路径可经缓存变量覆盖）；界面统一为 VS Code 风格深色主题（`QPalette` 调色板 + QSS 样式表），图标、样式与参数 JSON 全部编译进单一 exe，便于分发。

**● 项目成果**

- 独立完成覆盖抽象层、工厂、事件总线、参数面板、图像队列、渲染窗口的完整客户端软件，代码分层清晰、职责单一，模块平均 150~300 行；已在 Windows + VS2022 + Qt 6.10 环境编译运行并开源。
- 架构侧实现三项低成本扩展能力：新增相机品牌零修改既有代码、新增相机型号零代码、新增参数类型纯新增控件，相比硬编码方案的维护效率有结构性提升。
- 虚拟相机机制把开发与测试从硬件依赖中解放出来——参数面板、图像链路、事件总线等全部功能均可在无相机条件下调试与演示。

**● 技术复用性**

项目的抽象接口层、工厂注册机制、统一参数模型与生产者-消费者图像队列均为通用组件，可直接迁移到其他工业设备上位机（运动控制卡、PLC、光源控制器等）——把"相机"替换为任意设备类型即可复用同一套分层与解耦思路；JSON 驱动界面的方案亦可复用于任何需要批量参数配置的工控场景。

## 五、面试追问准备

| 面试官可能问 | 回答要点 |
|---|---|
| 为什么不用一个类把所有相机都写进去，非要接口 + 工厂？ | 讲变化点被关进了哪个盒子。可以拿其他厂商的接口差异举例：大华是 `DH_GetDoubleFeature`、Basler 是 `camera.ExposureTime.GetValue()`、海康是按类型分的 `MV_CC_Get*Value` 六套，接口层统一之后界面一行都不用改。 |
| 工厂模式和 Qt 插件（`QPluginLoader`）有什么区别？ | 编译期绑定 vs 运行期动态加载；单 exe 部署 vs 独立 DLL 按需部署；第三方能否独立开发；版本能否单独升级。本项目选工厂是因为依赖集中、部署简单，插件化是它明确的下一步演进方向。 |
| 参数模型为什么要做成组合式，直接 QVariant 存值不行吗？ | 直接存 QVariant 会丢掉取值范围、枚举候选、最大长度这些元信息，界面就无法生成正确的编辑器（比如枚举要 ComboBox、布尔要勾选框）；另外对外只有一个 `CameraParam` 类，类型差异被关在设备实现层，这是关键。 |
| 图像队列为什么要两个队列？一个队列不行吗？ | 单队列每次入队都要分配新内存、队列满只能丢新帧、内存还得手动管；双队列预分配帧内存并循环复用（稳态零分配）、满队列覆盖最旧帧（预览场景要的是最新画面）、出队即归还形成闭环，RAII 不用手动管理。 |
| 为什么选 QGraphicsView，不用 QLabel 直接显示？ | QLabel 不能缩放拖动；QWidget 手绘 `paintEvent` 要自己写坐标变换；QGraphicsView 自带场景-视图坐标变换、只渲染可见区域，缩放平移居中都是现成能力，后面接 ROI、测量工具也是在场景里加图元。 |
| 取流的时候改参数会怎样？你怎么处理的？ | 开流后参数面板整体禁用（事件总线通知），停流恢复。原因是采集过程中改 ROI 或像素格式会让帧尺寸与格式突变，缓冲区尺寸就对不上了。 |
| 这个项目的难点你觉得在哪？ | 建议答"统一参数模型 + 图像链路"这两个：一个解决"不同相机参数长得不一样"，一个解决"出图比界面快"。不要答"界面画得好看"。 |
| 项目里有没有你重构过的地方？ | 有素材就讲：比如把各处的错误码判断统一成 `CHECK_RETURN` 宏、把六种编辑控件重复的取值回写流程上提到基类、把型号相关的参数定义从代码里抽成 JSON。哪怕只是整理，也要讲清"重构前什么样、重构后什么样、为什么值得"。 |
| 加了新品牌之后，怎么保证参数面板能正常显示？ | 新品牌的参数靠它自己实现的 `getParamList` 提供元信息（可以走 JSON，也可以直接返回硬编码表），面板只认统一的 `CameraParam` 结构；权限靠 `MV_XML_GetNodeAccessMode` 这类接口拿，拿不到就按默认权限处理。 |
| 这套架构换个设备还能用吗？ | 可以。接口层、工厂、参数模型、图像队列都不依赖"相机"这个概念，把设备类型换掉即可；讲清楚哪些是真通用、哪些需要重写（比如参数权限的获取方式每家设备都不一样）。 |

**主动介绍时的一句话结构**：先说清"解决什么问题、给谁用"（相机厂商自带的 MVS 客户端没法嵌进用户自己的自动化系统，必须做 SDK 二次开发）→ 再说"我怎么分层"（接口 / 工厂 / 门面 + 参数模型 + MVD 面板 + 图像队列 + 事件总线）→ 最后说"我做了哪些取舍、为什么"。

## 六、投递前提醒

1. **架构图和界面图自己画**：不要去用训练营教材里的架构图，所有学员都可能用同一张，撞车概率很高。界面截图直接用你现在这个深色主题版本即可；架构图建议用 draw.io 重画一遍，配色和布局都改掉。
2. **按岗位调顺序**：投 C++/Qt 客户端、上位机、工业软件岗时，把"分层架构 + 统一参数模型 + 图像线程链路"放前面；投纯 Qt 客户端岗可以把 MVD 参数面板和 QGraphicsView 视觉窗口提前讲。
3. **日期要填真**：文中的 `2026.0X` 是占位符，按你实际开始做的时间填。项目周期太短（比如两周）反而会让面试官怀疑深度，可以写成从开始接触工业相机到功能收敛的整段跨度。
4. **不要写的几项**：不要写"支持大华 / Basler"（仓库里只有海康和虚拟相机两个实现）；不要写"实测稳定 60fps"这类没测过的指标；不要写"零拷贝"（`cvMat2QImage` 默认 `clone=true`，界面刷新处还有一次 `image.copy()`，实际是有拷贝的）；不要写"多相机同步采集"（枚举与切换支持，同步没做）；不要写 MVVM（实现的是 MVD）。
5. **数字要能守住**：4800 行、27 个 .cpp、31 个 .h、17 个接口、6 种参数类型、6 种编辑控件、37 个参数、5 个分组、队列 10 帧、5 秒超时、缩放 0.1×~50×、16 个错误码——这些都能在源码里数出来，写上去被追问不会翻车。
6. **代码是开源的，等于把源码交出去了**：投递前建议先修掉 `BoolCustomWidget` 里布尔参数按 `IntParam` 回写、`AcquireImageProcess` 线程无退出标志、`CameraImageQueue::Take` 超时返回值、`CameraContext::startGrabbing` 返回值被覆盖这几处，被面试官先翻出来比较被动。
